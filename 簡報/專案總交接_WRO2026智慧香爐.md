## 2. 專案定位與商業敘事

> 對應檔案：`智慧香爐_硬體設計交接.md` §0、`專案進度.md` §3B、`簡報/一分鐘講稿.md`

### 2.1 商業主打（2026-08-07 拍板）

**既有香爐的空品監測＋抽排過濾「改裝模組」（retrofit）。**

- 不換爐、不要求信眾改變任何行為
- 買方＝**廟方管委會**（B2B 單一決策者）
- 買點＝工安、環保陳情壓力、廟方公關（空品即時公開本身就是文宣）
- 商模＝硬體進場 ＋ 雲端多爐監測訂閱（**報表比風扇值錢**）
- 出海順序：新加坡／馬來西亞（法規推力）→ 香港（付費意願已證實）→ 日本／泰越 → 印度（最大量級）→ 歐洲教堂乳香

### 2.2 核心論述（第一性原理）

```
空汙濃度 = 產生速率 − 移除速率
產生端是信仰，動不得  →  所以只放大「移除端」
```

一句話結論：**「我們讓香繼續燒，但煙不再害人。」**

### 2.3 ★理香機構已整組移除★（2026-08-16 使用者決定）

原本最獨創的機構（插孔板／導正套筒／磁力矩陣電磁鐵 ×4／磁座）**全數自設計移除**。

**移除理由**（這是答詢時「你們遇過什麼挫折」的最佳答案，務必保留敘事）：

1. 插孔板要求信眾「對準孔、把香放進套筒」，與真實香爐「隨手插進香灰」的行為不相容 —— 人不會為機構改變行為，孔滿之後香只會插在孔外。
2. 尖峰時段一人三炷、一小時數百炷，遠超任何可行格數；理香只作用於套筒內的香。
3. 在插孔板真正成立的減香情境（一人一炷、定格插香），悶燒擠香問題本身大幅消失 —— **機構解決的問題被自己的前提消滅**。

閉環展示改由「**CO₂ 分級 → 風扇抽排 ＋ 超音波霧化煙源**」承擔。
舊設計見 git 歷史（`e8171aa`、`54eb8fe` 等）。

**⚠️ 交接注意**：`智慧香爐_硬體設計交接.md` 中所有理香相關段落（§0 部分、§1A-C 電磁鐵、腳位表 D7/D8、§7 機構規格）**僅為歷史紀錄，勿再據以採購或實作**。

### 2.4 另一個「敢改」的故事：集煙罩漏斗化（2026-08-16）

原設計上窄下寬縮口（罩頂 96mm）→ 使用者反映不好插香 → 改為
**下段直筒 44mm（煙道開口與風扇座法蘭靠垂直後壁）＋ 上段外擴喇叭口至 180mm**（內開口 ≈175）。
喇叭斜面 34°，倒印自支撐。「為使用者行為改設計」是加分敘事。

## 3. 系統架構（現行兩板架構）

> 對應檔案：`專案進度.md` §3、`P0接線與驗證指南.md`（頂部架構變更框）

### 3.1 現行架構

```
┌─ MATRIX Mini R4（感測 ＋ 安全 ＋ 致動）────────────────┐
│ SCD41(I²C1) · SHT31(I²C2) · MAX6675 K型熱電偶(SPI)     │
│ DS18B20(A2) · OLED · 本地簡化 FSM · 超溫聯鎖           │
│ 風扇 PWM → D4184 → 12V 5015 鼓風機                     │
└──────────────┬─────────────────────────────────────────┘
               │ USB-C 序列 115200（udev 固定名 /dev/r4）
               ▼
┌─ Raspberry Pi 5 16GB（決策 ＋ 審計 ＋ 上雲）───────────┐
│ pi_fsm.py：S0/S1/S2/S3 狀態機、CO₂ 前饋、每秒 JSONL    │
│ 本機 mosquitto → 橋接（QoS1 佇列）→ 雲端               │
│ 本機 Docker 監測棧（InfluxDB:8087 / Telegraf / Grafana）│
└──────────────┬─────────────────────────────────────────┘
               │ MQTT（Tailscale）
               ▼
┌─ 雲端中心站（家裡桌機 WSL2 Ubuntu 24.04）──────────────┐
│ mosquitto + InfluxDB 2.7 + Telegraf 1.30 + Grafana 11.2│
│ Tailscale Funnel → 3 個免帳密公開唯讀儀表板             │
└─────────────────────────────────────────────────────────┘
```

### 3.2 為什麼是兩板（2026-08-02 拍板，2026-08-07 三板殘留全刪）

原設計是三板（ESP32-S3 感測 ／ R4 安全致動 ／ Pi 5 決策）。
發現使用者的控制器是 **MATRIX Mini R4**（基於 Arduino UNO R4 WiFi，內建 I²C 埠、5V 供電）後改為兩板。

**失去**：
1. **感測器擺位自由**（最實際）— I²C 線長受限：單顆上拉 10kΩ → 約 1m；雙上拉並聯 5kΩ → 約 2m。超過就得回頭用 WiFi。
2. 「S3 失效 → R4 仍保安全」這層降級消失（但誠實地說：R4 本來就已是致動的單點故障）。
3. 報告的「三層獨立」論述要重寫。

**得到**：
1. **降級階梯不消失，只是換形狀，且 Pi 失效那層變強** —— 原本 R4 只能吐固定 `FALLBACK duty 80`（不知 CO₂ 多少）；合併後 MATRIX 有 CO₂ 讀值，可在本地跑簡化 FSM 做真正的回饋控制。
2. 少掉整類失效模式（S3↔Pi 的 WiFi、MQTT 斷線誤判）。
3. 反應變快（少三跳）。

**前提**：感測頭離控制盒在 1–2 公尺內。若日後佈置超出線長限制要回頭用三板，從 git 歷史取回（刪除前最後版本：commit `2f5ab86` 之後的工作區）。

### 3.3 故障安全階梯（現行）

| 失效點 | 系統行為 |
|---|---|
| 雲端／網路斷 | Pi 本地續跑，本地 Grafana 照常；橋接 QoS1 佇列積壓，回線自動補傳 |
| Pi 失效／序列逾時 5s | R4 進 **FALLBACK**，用自己的 CO₂ 讀值跑本地簡化 FSM |
| 感測失效 | 回傳 `-99.9` 誠實故障值，`sensor_fault` 旗標；安全態優先 |
| 超溫 / 熱電偶開路 | R4 就地聯鎖，**直接拉低 PWM 腳**，風扇強制 0，無軟體介入路徑 |
| 全系統斷電 | 香爐回復傳統使用（無任何機構阻礙插香） |

### 4.4 供電樹

```
市電 → 12V 3A 變壓器 ──┬─ 保險絲 2A（必加）
                        ├─ A1 MATRIX VIN（板子吃 6–24V）
                        ├─ U6 D4184 → M1 5015 風扇（0.2A）
                        └─ U7 PCF8574板 → M2 霧化模組 ＋ LED1 罩內LED
Pi 5 → ★官方 27W USB-C 專用電源★（不可共用；低壓重置正是 SD 卡的死因）
```

- **一顆 12V 同時餵板子與風扇，共地自動成立。**
- **12V 絕不可碰到 3V3／5V 排。**
- **★馬達埠推不動 12V 風扇★**：`MatrixMiniR4.h` 寫明 `Port M1 DC 5V Motor`，是穩壓 5V 輸出不是 6–24V 直通。**D4184 ＋ 獨立 12V 必須保留。**

### 4.5 為什麼風扇不走馬達埠（即使有 12V 轉接板也不走）

風扇是**安全致動器**，超溫聯鎖必須能確實停機：

| | D4184（採用） | 馬達埠＋轉接板 |
|---|---|---|
| 控制路徑 | RA4M1 → PWM 腳 → MOSFET | RA4M1 → **STM32 副處理器** → 馬達驅動 → 轉接板 |
| 聯鎖停機方式 | **直接拉低 PWM 腳，無軟體介入** | 需 STM32 正確執行命令 |

控制鏈多一顆 MCU 就多一個「它當掉時風扇維持原轉速」的失效模式。另外馬達驅動是 H 橋（雙向），2 線無刷風扇只需單向，H 橋高側自舉常做不到 100% duty，反向驅動還可能傷及風扇內部換相電路。

### 5.2 Pi 決策層 FSM（`pi_fsm.py`）

**狀態**：S0 待機 ／ S1 常態 ／ S2 高峰 ／ S3 異常

**★門檻相對於背景基線，不是絕對值★**（2026-08-07 改，與 R4 韌體同步）：

```python
CO2_IDLE_DELTA = 50      # 高於基線 <50 且持續 → S0
T1_DELTA       = 300     # 高於基線 300 → 進 S2（呼氣即可達到）
T1_EXIT_DELTA  = 200     # 退 S2（遲滯）
BASELINE_WINDOW_MIN = 10
CO2_BASELINE_INIT   = 450
SLOPE_TH       = 120.0   # ppm/min，CO2 前饋門檻 θ_ff
IDLE_HOLD_S    = 60
SENSOR_STALE_S = 10
DUTY = {"S0": 0, "S1": 70, "S2": 220, "S3": 0}   # 0-255
```

**為什麼改成相對基線**：絕對門檻只在背景穩定時成立。安靜的廟宇清晨約 450ppm，人多的展場大廳 1000–2000ppm —— **用絕對值在展場會永遠卡在 S2、S0 永遠到不了，分級響應完全看不出來**。

**基線演算法**：過去 10 分鐘內「每分鐘最小值」的最小值。
★取最小不取平均★ —— 要的是「沒人時的底」；用平均會被人潮拉高，變成「人越多門檻越高」的正回饋，方向剛好相反。

**其他**：
- `SERIAL_PORT = "/dev/r4"`（udev 固定名 `99-r4.rules`，重列舉不再跳 ACM0/ACM1）
- 每秒寫一筆 JSON Lines 決策紀錄（可重演）＋ publish 到 `incense/decision`
- 轉發白名單已加 `t_ds`（★僅筆電副本，Pi 上尚未更新★）

**決策紀錄格式**：
```json
{"ts":"2026-07-30T14:03:21","co2":1420,"slope":260.0,"t_sht":26.2,"rh_sht":61.0,
 "conf":1.0,"s3_alarm":0,"t_furnace":27.25,"fan_actual":220,"r4_mode":"PI",
 "interlock":0,"state":"S2","fan_duty":220,"action":"S1->S2"}
```

### 7.3 核心設計約束是「熱」

熱電偶聯鎖 150/130°C（臨時值），而 **PLA 的 HDT 只有 55–60°C**。四道設計對策：

1. 燃燒由**金屬爐盆**（外購不鏽鋼碗）承接，塑膠不碰火源
2. 爐盆與塑膠之間留 **8mm 空氣間隙**（最好的絕熱材）
3. 燃燒艙↔電子艙之間 **14mm 隔熱層 ＋ 對流通風縫**
4. **燃燒艙與集煙罩必須用 ABS/ASA/PETG，不可用 PLA**

**感測器艙裝在前方朝外而非煙道內**，理由有二：
- FSM 用 CO₂ 斜率偵測人潮，要量的是「參拜者呼吸到的空氣」
- SCD41 工作溫度上限約 60°C，放煙道會壞

### 7.4 過濾鏈（★順序即安全★）

```python
FILTER_CHAIN = ["金屬紗網", "HEPA", "活性碳濾棉"]   # 順序不可調換
FILTER_PRESSURE_DROP_PA = {"金屬紗網": 5.0, "HEPA": 120.0, "活性碳濾棉": 40.0}
FAN_STATIC_PRESSURE_PA  = 250.0   # ★估值，未實測★
```

- **金屬紗網必須在 HEPA 之前** —— 風扇抽香煙＝把未熄火星往濾網吸，而 HEPA 是可燃物。紗網是安全件，必在最前。
- 活性碳在 HEPA 之後，否則會先被灰堵死。
- **風扇置於最末＝抽拉式**：推吹式讓扇葉先吃滿香灰油煙（葉形改變、動平衡跑掉、風量衰減、清潔困難）；抽拉式扇葉只碰濾後乾淨空氣。代價：濾箱必須氣密（負壓下漏氣＝髒空氣旁通），組裝時接縫打膠。
- 鼓風式（5015）靜壓遠高於同價軸流扇，推得動 HEPA 壓損；軸流扇會在濾網前「空轉」。

### 7.5 無明火展示機（2026-08-07）

大會禁明火。關鍵事實：**整條決策鏈根本不靠煙** —— FSM 只看 CO₂ 濃度與斜率，而 CO₂ 來自人的呼吸。**會場圍在攤位前的評審與觀眾本身就是訊號源。**

| 原本靠火 | 無火替代 |
|---|---|
| 看得見的煙 | 超音波霧化（冷霧，不放 CO₂）＋ 罩內 LED 側光 |

**★乾冰不能用★**：它是 CO₂ 源，會頂穿 1500ppm 硬警報讓風扇整場全速、分級一次都展示不出來；論述會被自己汙染（量到的是乾冰不是人潮）；冷霧又下沉，集煙罩抓不到。

**兩種建置組態**（`mech_params.py` 的 `BUILD_CONFIGS`）：

| 組態 | open_flame | 近爐溫度 | 說明 |
|---|---|---|---|
| **展示機**（`CURRENT_BUILD`） | False | 35°C（＝感測器艙） | 香不點燃 → **根本沒有熱區** |
| 廟宇爐 | True | 120°C | 實地佈署，真的燒香 |

> ★廟宇爐的耐熱衝突沒有被藏起來★：它會進 `pending_build_conflicts()`，每次跑測試都印出來。

**兩個只有實體才知道的未知**：
- 冷霧不像熱煙會自然上升，靠鼓風機抽吸拉進集煙罩 —— 集煙罩對非浮升煙源抓不抓得到，**只有實體吹過才知道**
- **任何霧都可能觸發場地的煙霧偵測器**（水霧也不例外，光電式偵測器靠散射光判定）—— 只有問主辦單位才知道

### 8.3 ★最有價值的發現★：3.3V 訊號接不進 R4 的數位腳

（三板時期的歷史紀錄，但**結論仍然重要**）

```
原設計：S3 GPIO4 (3.3V) ──直接接──> R4 D2（數位腳）
R4 (RA4M1) 數位輸入 VIH = 0.8 × VCC = 4.0V
餘量 = 3.3 − 4.0 = −0.7V   ✗ 規格上讀不到 HIGH
```

原指南寫「3.3V 是邊界值、實務上幾乎都過」—— 那是 UNO **R3**（ATmega328P，VIH = 3.0V）的經驗。UNO **R4** 換 RA4M1 後門檻升到 4.0V，同一條線不再成立。

**這條線正是「Pi 當機時保命」的硬體旁路，平常完全測不出來。**

**採用解法：改接類比腳 A0（零元件）**
```
S3 拉高 3.3V → ADC ≈ 675/1023 ；放開 0V → ADC = 0
韌體門檻 > 500 判警報、< 300 才解除（軟體遲滯，取代數位腳的施密特輸入）
兩側餘量 175 / 500 counts
```

**★不可用 BSS138 雙向模組★**：S3 斷電時其 HV 側 10kΩ 上拉會讓 R4 誤讀成警報中、風扇鎖死全速，反而破壞降級行為。加下拉去壓制又會與上拉分壓成 2.5V，正常運作時反而失效 —— **兩種情況無法兼顧**。

**其他方案**：74**HCT**125／14 可行（HCT 是 TTL 準位 VIH=2.0V）；74**HC**125 與 CD4050B **不行**（VIH = 0.7×VCC = 3.5V，一樣不夠，而且 HC/HCT 外觀腳位相同極易買錯）。

> 兩板架構後警報線整條取消，但 **RA4M1 VIH = 4.0V 這個結論仍然重要** —— 日後任何 3.3V 訊號要接進這塊板子的數位腳都會遇到同樣問題。

### 8.4 其他電氣驗算重點

| 項目 | 結果 |
|---|---|
| R4 PWM → D4184 閘極 | ✅ 5V 推挽驅動綽綽有餘；模組通常已含閘極下拉（未初始化時風扇不誤啟動） |
| 風扇電流 vs D4184 | ✅ 0.2A vs 15A，約 75 倍餘量；啟動突波 ≈0.6A 仍在範圍內 |
| I²C 匯流排 | ✅ tr ≈ 210ns vs 上限 1000ns，約 4.7 倍餘量；`Wire.setClock(100000)` |
| MAX6675 ↔ R4 | ✅ 兩端同 5V 直接相接；轉換 220ms，輪詢 ≤4Hz |
| 12V 電源預算 | ✅ 3A 電源，展示機實際負載遠低 |
| **風扇 PWM 頻率** | ⚠️ **需調參** —— 預設 490 Hz 落在可聽範圍會嘯叫，建議用 R4 核心 `pwm.h`(PwmOut) 拉到 **25 kHz** |
| **S1 duty = 70** | ⚠️ 可能低於無刷風扇最低啟動占空比（常見 30–40%，即 77–102），需實測 |

**2 線無刷風扇的取捨**：只能低側斬波供電，內部換相電路跟著斷電。頻率太低（數百 Hz）→ 反覆重啟、轉速不穩；太高（25kHz）→ 內部電容濾波後接近直流，較穩且無嘯叫。若實測仍不穩，正規解法是換 **4 線 PWM 風扇**（獨立 PWM 腳，不斬斷主電源，資料中心標準做法）。

### 9.1 為什麼長這樣：★AI 看不到的東西★

## 10. 工作規則與★紅線★

> 對應檔案：`CLAUDE.md`（每次工作前必讀）、`.claude/commands/verify.md`

### 10.1 ★紅線★（違反即視為任務失敗）

1. **修改測試斷言**或放寬驗證器容差，以讓輸出變綠
2. **放寬安全與可製造性下限**：壁厚、氣隙、耐熱溫度、列印最小特徵等下限
3. **規避禁 PLA 區**：把近爐零件改用 PLA，或把零件標成 `near_censer=False`
4. **調換 `FILTER_CHAIN` 順序** —— 金屬紗網必須在 HEPA 之前（火星防護）
5. **把 `*_MEASURED` 旗標改成 `True`** —— 只有人實際量過才能改
6. 用 `skip` / `try-except-pass` / 註解掉測試來消除失敗
7. **宣稱需要實體硬體或目視才能確認的事項「已驗證」**

參數之間衝突到無解時，正確反應是**回報衝突並提出取捨方案**，讓人決定 —— 那是設計決策，不是 agent 該自己選的。

### 10.2 一般原則

- 動任何設計參數前，先跑一次驗證看現況；改完再跑一次，比較差異
- 失敗時**修設計，不修測試**
- 不確定該怎麼取捨時，依 §10.4 回報卡關，不要猜

### 10.3 硬體邊界：永遠人在迴路

以下**無法**由任何自動檢查取代：
熱變形實測｜氣流與抽排效能｜插香手感與人因｜列印件強度與耐久｜外觀與文化適切性（廟方觀感）｜韌體實機燒錄行為


## 11. 誠實邊界（對外可以說什麼、不可以說什麼）

> 這是本專案的核心價值主張之一，也是評審加分項。**接手者務必嚴格遵守。**

### 11.1 「設計目標」vs「實測值」

`mech_params.py` 中所有 `*_MEASURED = False` 的項目都是**估計值**。基於它們的任何數字，在報告中**只能稱「設計目標」**，不能寫成實測結果。

**目前未實測清單**（`unmeasured_items()`）：
1. 香爐內徑／深度
2. 近爐區實際溫度
3. 風扇靜壓（含過濾壓損下的實際風量）
4. 風扇啟動突波倍率
5. 感測器艙實際溫度
6. 超音波霧化模組實際電流

**優先量測順序**（`.claude/commands/verify.md` §6）：
1. **香爐內徑與深度** —— retrofit 模組要架在真爐上，量錯整個外形重來
2. **近爐區實際溫度** —— 用 MAX6675 直接量，同時驗證禁 PLA 區範圍與聯鎖門檻
3. **風扇靜壓與啟動突波** —— 決定過濾鏈選型與電源餘裕的真實性
4. **霧化模組實際電流**
5. **感測器艙實際溫度** —— SCD41 上限 60°C 的安全餘裕

### 11.2 ★聯鎖門檻 150/130 是臨時值★

原本 80/60 低於熱電偶位置的預估工作溫度（120°C），正常燃燒就會鎖死風扇（聯鎖優先權高於一切）。2026-08-02 提高為 150/130，但這**沒有實測依據**，只是「先讓系統跑起來」。

`T_LOCK_PROVISIONAL = True` 追蹤這件事。**實測熱電偶位置的真實溫度後必須重定，報告在那之前不得將此門檻描述為已驗證的安全設定。**

### 11.3 ★資料真偽邊界★

- **`aroma02` 是 `sim_burner.py` 產生的模擬資料** —— 任何展示、報告、簡報都必須明確標示為模擬機
- **`aroma01`** 自 **2026-08-08 01:15（台北）** 起是真實 Pi5＋R4 的實測資料
  - 但 InfluxDB 裡該時間點**之前**的 aroma01 歷史（2026-07-30 起）是當時模擬器發的
  - aroma01 實測資料在兩處：雲端（08-08 01:15 ～ 08-09 Pi 斷線）與 Pi 本地新棧（08-10 起），**中間有斷層**（SD 故障停擺期）
  - 引用任何連續區間都必須註明
  - 補傳資料的 InfluxDB 時間戳是**到達時間**非量測時間

### 11.4 講稿可以說 / 不可以說

| 可以說 | 不可以說 |
|---|---|
| 「原型已實機上線，感測資料每秒進雲端面板」（指感測—決策—雲端**資料鏈**） | 抽排降污的**成效數字**（H1–H3 全未實測） |

## 14. ★專案特有的坑★（踩過的，不要再踩）

> 這是 `CLAUDE.md` §4 的完整清單，接手第一天就該讀。

1. **MATRIX Mini R4 的 D2、D3 埠不能用**。`MiniR4.begin()` 內執行 `PS2.config_gamepad(11, 4, 12, 5)`，把腳 11/4/12/5 佔為手把介面。**只用 D1、D4**。

2. **MatrixMiniR4 函式庫（≤1.2.5）與 Adafruit BusIO 連結衝突**。該庫把 `Adafruit_I2CDevice` 整個類別抄進 `src/Modules/MiniR4_I2CDevice.cpp`，與 Adafruit_SHT31 相依的正牌 BusIO **十個符號全數重複定義**（multiple definition）。
   已在使用者函式庫以 `#if !__has_include(<Adafruit_I2CDevice.h>)` 包住整檔讓位 ——
   ★**函式庫一更新補丁就消失**★，連結錯誤重現時照 2026-08-08 的做法重加。

3. **Arduino 草稿本位置因機而異**：
   - 桌機：`C:\Users\feihong\OneDrive\文件\Arduino`（**不是** `Documents\Arduino`）
   - 筆電：`C:\Users\feihong\Documents\Arduino`（BusIO 讓位補丁已重加在該副本）
   - arduino-cli 在 `C:\Users\feihong\Arduino IDE\resources\app\lib\backend\resources\`

4. **UNO R4 的 `snprintf` 不保證支援 `%f`**。組 JSON 用 `Serial.print(x, 2)`。

5. **馬達埠是 5V**（`Port M1 DC 5V Motor`），推不動 12V 風扇，**D4184 必須保留**。

6. **UNO R4 WiFi 內建的 ESP32-S3 不能替代獨立開發板** —— 它是網路協處理器，GPIO 一支都沒拉到排針，不能讀感測器、不能控風扇（PWM 屬於 RA4M1）。只能做網路。

7. **Grafana Public Dashboard 不代入模板變數**，且**文字型欄位在 stat 卡片顯示不出來**（解法見 §6.3）。

8. **KiCad 的 `power_pin_not_driven`**：每條電源網路要有 `power_out` 或 `PWR_FLAG`。

9. **OpenSCAD 的 `Volumes` 不是 2 代表有浮空塊** —— 參數檢查看不出來，只有算繪才知道。

10. **Windows 的 .exe 看不到 WSL 的 `/tmp`**，暫存檔要放在 `/mnt/` 底下。

11. **OpenSCAD 的 `include`／`use` 路徑不吃非 ASCII**。中文檔名或中文目錄一律回報 `Can't open include file`，錯誤訊息本身是 CP950，`text=True` 的 subprocess 會直接丟 `UnicodeDecodeError`。註解裡的中文沒問題，**只有路徑不行** —— 所以 `外觀CAD/` 底下被 include 的 `.scad` 與其目錄一律用 ASCII。

12. **`use <>` 不帶變數** —— 零件檔裡定義數字會讓 `incense_burner.scad` 算成 `undef`，幾何空掉時交集永遠 0，**檢查會靜默通過**。

13. **`part` 名稱打錯要 assert 失敗，不能靜默退回 `assembly()`** —— 否則匯出 STEP 時每個元件都在算整台機器，一個爐盆跑十幾分鐘才發現。

14. **爐面的條紋是 F5 預覽假影**（OpenCSG 對半透明物件不做深度排序），按 F6 就沒了。

15. **MAX6675 模組整個未接時 SPI 讀全零**，`tc_fault=0`、`t_furnace=0.00` —— 韌體只能偵測熱電偶開路，**判不出模組缺席**，接線日勿誤判。

16. **DS18B20 不能插 D1** —— D1 左（腳 3）是風扇 PWM、右（腳 2）是 MAX6675 CS；函式庫 `MXOnewireDT` 用埠的左腳。A1/A2 是僅存空埠。

17. **usb-watchdog v1 判不出「枚舉在但主迴圈死了」** —— 08-12 R4 卡死事件（OLED 凍結＝整個主迴圈卡死，顯示／感測／telemetry 同一個 loop）。v2 已加測「`incense/sensor` 15 秒無訊息」。

18. **Pi5 的 `uhubctl` 埠「斷電」實際上不切 VBUS**（R4 uptime 不歸零），只做重新協商 —— 可救 CDC 軟卡死，救不了完全消失。

19. **R4 斷電後不會自動開機**，必須手動按電源鍵（看門狗無法軟體代按）。

20. **KiCad 開著檔案時重跑產生器**：不會自動重載且會留下 `.lck`，請關閉專案再重開。

21. **系統 Python 受 PEP 668 保護** —— 不要用 `--break-system-packages`，需要套件請開 venv。

## 附錄 A：一分鐘講稿（定稿）

> 約 150 字，35–40 秒。口語提示：結論那句放慢講重；「燒香是信仰欸」用平常聊天的語氣；最後一句慢慢收。

先講結論：**我們讓香繼續燒，但煙不再害人。**

全球有二十二億人拜拜要燒香——佛教、道教、印度教都是。但香的煙就是 PM2.5，就是致癌物，而且每天都在廟裡累積。

這問題為什麼一直解決不了？因為以前的做法都在叫人少燒——減香、禁香、電子香。但燒香是信仰欸，怎麼禁都會讓信眾覺得被冒犯、心裡不舒服，所以每次都推不動。

我們反過來想：燒多少不是重點，重點是煙留在那裡多久。所以我們做了智慧香爐——濃度一高，風扇自己轉、自己過濾，過熱還會自動斷電。

香照燒，神明照拜，煙不見了。健康跟信仰，不用二選一。

## 附錄 B：答詢口袋（Q&A 素材）

| 評審可能問 | 回答骨幹 |
|---|---|
| 你們遇過什麼挫折？ | **理香機構整組移除** —— 曾投入開發磁力理香，檢討後確認與信眾自由插香行為不相容而整組刪掉（§2.3） |
| 為什麼改設計？ | **集煙罩漏斗化** —— 原為上窄下寬縮口不好插香，改為漏斗大口＋下段直筒接風扇法蘭（§2.4） |
| 為什麼不用攝影機數人頭？ | 廟宇場域隱私敏感＋光線多變＋算力成本；一顆 CO₂ 感測器優雅得多，且人呼出的 CO₂ 比插香高峰**早數分鐘**上升 |
| 為什麼不用便宜的 MQ 系感測器？ | 半導體式會被酒精與煙氣嚴重干擾，在香煙環境形同失明；NDIR 量的是 CO₂ 分子真實紅外吸收，穩定不中毒 |
| 為什麼把最重要的安全交給最弱的板子？ | 正因為它最簡單 —— 沒有 OS、沒有網路協定棧、沒有動態記憶體，當機面最小、行為最可預測。**安全工程的鐵律是「安全功能放在最不會壞的地方」** |
| 風扇為什麼放在濾網後面？ | 抽拉式扇葉只碰濾後乾淨空氣（推吹式會吃滿香灰油煙導致葉形改變、動平衡跑掉）。代價是濾箱必須氣密 |
| 為什麼金屬紗網一定在最前？ | 風扇抽香煙＝把未熄火星往濾網吸，**而 HEPA 是可燃物**。紗網是安全件 |
| 你們的數字有多可靠？ | 我們有制度化的 `*_MEASURED` 待實測清單，未實測的一律稱「設計目標」；模擬機資料明確標示。**主動揭露不確定性比假裝精確可信** |
| 系統壞了會怎樣？ | 逐級降級（§3.3）；最終狀態是「香爐回復傳統使用」—— 斷電＝不動＝香爐照常用 |
| 為什麼是現在？ | 環保陳情壓力、廟方公關需求、低成本感測器與邊緣算力成熟三者同時到位 |
