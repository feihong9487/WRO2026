# 智慧香爐 — 物聯網多爐平台指南
（多爐監測・使用者/工程師登入・開機即上線・遠端維修與更新）

在上一份《雲端監測平台指南》的基礎上升級。原有單機部署完全不用拆：本指南只「加」三塊——雲端中心站、每爐橋接、Tailscale 維運通道。

---

## 0. 全景

```
香爐節點（每台一組，韌體所有爐相同）
  S3 ──WiFi──→ Pi 5：mosquitto（本地）＋ pi_fsm.py（FSM＋JSONL 審計）
                └─ mosquitto bridge（QoS1，斷線佇列）──→ 雲端

雲端中心站（一台：家中舊電腦/第二台Pi/免費雲主機）
  mosquitto（帳密驗證）→ Telegraf（從主題解析出爐號標籤）→ InfluxDB → Grafana

維運通道：所有 Pi＋雲主機加入同一個 Tailscale 私網（WireGuard 加密、不開公網埠）
使用者入口：Grafana 登入（Viewer/Editor/Admin 分權）；對外用 Tailscale Funnel 取得 HTTPS 網址
告警：Grafana Alerting → Discord/Telegram → 手機推播
```

主題命名空間：每台爐的本地主題維持 `incense/sensor`、`incense/decision` 不變；橋接自動改寫為 `incense/{爐號}/sensor|decision` 上雲。**身分只存在於 Pi 上的一個設定檔，S3/R4/Pi 程式所有爐同一份。**

## 1. 雲端中心站部署（約 30 分鐘）

主機選擇：家中舊電腦或第二台 Pi（走 Tailscale 免固定 IP，$0）／Oracle Cloud 免費層／小型 VPS。以下假設是一台 Debian/Ubuntu 系主機。

```bash
# 裝 Docker 與 Tailscale
curl -fsSL https://get.docker.com | sh
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up          # 登入後記下這台的 Tailscale IP（100.x.y.z）
tailscale ip -4

mkdir -p ~/incense-cloud && cd ~/incense-cloud
# 放入 cloud-docker-compose.yml、cloud-mosquitto.conf、cloud-telegraf.conf
mv cloud-docker-compose.yml docker-compose.yml
touch passwd
docker compose up -d

# 建 MQTT 帳號（橋接用 burner、Telegraf 用 telegraf；密碼自訂要記下）
docker compose exec mosquitto mosquitto_passwd -b /mosquitto/config/passwd burner   '你的橋接密碼'
docker compose exec mosquitto mosquitto_passwd -b /mosquitto/config/passwd telegraf '你的telegraf密碼'
docker compose restart mosquitto
# 把 cloud-telegraf.conf 裡的 telegraf 密碼改成剛設定的，然後：
docker compose restart telegraf
```

Grafana 設定（`http://<雲主機IP>:3000`，admin / incense12345，登入後立刻改密碼）：

1. Data source → InfluxDB → Flux → URL `http://influxdb:8086`、Org `incense`、Token `incense-local-token`、Bucket `incense` → Save & test。
2. Dashboards → Import → 上傳 `grafana_dashboard_fleet.json` → 選這個資料來源。

對外網址（給廟方用瀏覽器看，不必裝任何東西）：

```bash
sudo tailscale funnel --bg 3000     # 第一次會給你一個核准網址，照提示啟用
# 完成後獲得 https://<主機名>.<你的tailnet>.ts.net 的公開 HTTPS 入口
```

## 2. 香爐節點升級（每台約 5 分鐘）

前提：這台 Pi 已照 P0 指南跑起來（mosquitto、pi_fsm.py 可手動執行）。把 `provision.sh`、`incense-fsm.service`、`pi_fsm.py` 放同一個資料夾：

```bash
chmod +x provision.sh
sudo DEVICE_ID=aroma01 CLOUD_MQTT=100.x.y.z MQTT_USER=burner \
     MQTT_PASS='你的橋接密碼' TS_AUTHKEY=tskey-auth-xxxx ./provision.sh
```

- `DEVICE_ID`：爐號（建議 廟名縮寫+編號，例 ssjyg01）。
- `CLOUD_MQTT`：雲主機的 Tailscale IP。
- `TS_AUTHKEY`：到 Tailscale 管理頁 Settings → Keys 產生 auth key（可重複使用型），讓佈建全自動；省略則事後手動 `sudo tailscale up`。

腳本做的事：設定主機名 `incense-{爐號}`、寫入橋接設定與 10 萬筆佇列上限、安裝並啟用 `incense-fsm` 開機服務、啟用 Docker 開機自啟、加入 Tailscale。

驗證：

```bash
sudo systemctl status incense-fsm            # active (running)
mosquitto_sub -t 'incense/#' -v | head       # 本地主題正常
# 到雲主機上：
docker compose exec mosquitto sh -c "mosquitto_sub -u telegraf -P '密碼' -t 'incense/#' -v" 
#（應看到 incense/aroma01/sensor ...）
sudo reboot                                   # 重開機後不碰鍵盤，雲端面板應自動恢復資料
```

**新增一台爐 ＝ 燒同一份韌體 ＋ 跑一次 provision.sh（換爐號）**，儀表板下拉選單會自動出現新爐（標籤自動探索）。

## 3. 部署網路模式（廟宇現場）

- 對外連線首選：4G USB 網卡或隨身路由器＋物聯網 SIM（廟方 WiFi 不可控）。
- S3 的網路：讓 Pi 開熱點，所有爐的 S3 韌體因此完全相同——

```bash
sudo nmcli device wifi hotspot ifname wlan0 ssid incense-local password '香爐專用密碼'
sudo nmcli connection modify Hotspot connection.autoconnect yes
```

S3 韌體參數統一填：`WIFI_SSID="incense-local"`、`MQTT_HOST="10.42.0.1"`（NetworkManager 熱點的固定閘道位址）。

注意：Pi 內建 WiFi 當熱點時，**對外請走乙太網路或 4G 網卡**，不要讓同一顆 WiFi 晶片又當 AP 又當 client。實驗室階段維持原本大家連家用 WiFi 即可，不用急著切換。

## 4. 帳號與分權

| 角色 | 給什麼 | 能做什麼 |
|---|---|---|
| 廟方／一般使用者 | Grafana Viewer 帳號（或唯讀分享連結） | 手機/電腦看所有面板、在 Discord 群收告警 |
| 工程師（你們兩位） | Grafana Editor ＋ Tailscale 成員 | 編輯面板、SSH 進任何一台爐維修、刷韌體 |
| 管理者（教練） | Grafana Admin ＋ 雲主機/Tailscale 管理權 | 開帳號、加新爐、發佈建金鑰 |

Grafana 開帳號：Administration → Users → Invite（自架版直接 New user）。Tailscale 免費方案（3 使用者/100 裝置）足夠此規模，額度以官網為準。

## 5. 手機即時監測與主動告警

- 面板：手機瀏覽器開 Funnel 網址登入即可，選單「加入主畫面」就像 App。
- 主動推播（LINE Notify 已於 2025 年停止服務，改用 Discord 最快）：
  1. 建一個 Discord 伺服器與頻道 → 頻道設定 → 整合 → Webhook → 複製網址。
  2. Grafana → Alerting → Contact points → 新增 Discord，貼上 Webhook。
  3. Alert rules 建三條（皆 by device，告警訊息自動帶爐號）：
     - `sensor.co2 > 1500` 持續 1 分鐘 → 濃度異常
     - `decision.t_furnace > 80` → 高溫/聯鎖事件
     - 任一爐 5 分鐘無資料（規則的 No data 行為設為 Alerting）→ 離線告警
- Telegram 亦內建支援（建 bot 取 token），擇一即可。

## 6. 遠端維修與更新

所有機器都在 Tailscale 私網內，工程師在任何網路（含手機熱點、手機上的 Termius App）都能：

```bash
ssh pi@incense-aroma01        # Tailscale 提供私網 DNS，主機名直達
```

### 6.1 更新 Pi 端（最常見，十秒級）
```bash
scp pi_fsm.py pi@incense-aroma01:/tmp/
ssh pi@incense-aroma01 "sudo cp /tmp/pi_fsm.py /opt/incense/ && sudo systemctl restart incense-fsm"
```
（建議之後把程式放 GitHub，更新改成 `git pull`＋restart 一行。）

### 6.2 遠端刷 S3 韌體（三板時期紀錄，現行兩板架構已無 S3）
> 2026-08-07 兩板定案：獨立 ESP32-S3 與其韌體已移除，感測由 MATRIX Mini R4
> 直讀。本節保留當時的 esptool 刷寫流程供歷史參考；現行控制器更新
> 見 §6.3 的 R4 路線。

```bash
# （三板時期）Pi 當刷寫站：
scp s3_sensor_node.ino.merged.bin pi@incense-aroma01:/tmp/s3.bin
ssh pi@incense-aroma01
  pip install esptool --break-system-packages     # 第一次
  ls /dev/ttyACM*                                  # 分辨哪個是 S3（另一個是 R4）
  esptool.py --chip esp32s3 --port /dev/ttyACM1 write_flash 0x0 /tmp/s3.bin
```

### 6.3 R4：定位為「幾乎不更新的安全底座」
安全聯鎖層本來就該極少變動——會常調的門檻與邏輯都放在 Pi 端，這是設計美德而非限制。真需要遠端刷 R4 時走 DFU 路線（對序列埠做 1200bps 觸碰進 bootloader，再用 `dfu-util` 寫入；確切旗標可從 Arduino IDE 開啟詳細輸出的上傳訊息照抄）。建議在 P1 階段先在桌上演練一次這條流程再帶去現場。

## 7. 多爐展示（現在只有一套硬體也能 demo）

```bash
python3 sim_burner.py aroma02 --host <雲主機TailscaleIP> --user burner --password '橋接密碼'
python3 sim_burner.py aroma03 --host ... &   # 要幾台開幾個
```

虛擬爐每 4 分鐘模擬一波「人潮」：CO₂ 緩升緩降、狀態 S1↔S2 切換、爐溫與風扇連動。面板下拉選單與總覽磁磚會自動出現。**展示與報告中務必標明哪些是模擬機**（誠實一致性）；它的正當用途是驗證平台的多裝置擴充性，不是偽造第二台原型。

| # | 操作 | 預期 |
|---|---|---|

## 9. 已知限制與第二期路線（答詢誠實區）

- **續傳時間戳**：佇列補傳的資料在雲端以「到達時間」入庫，斷線期間的點會擠在重連瞬間；審計級時間軸以各爐本地 JSONL 為準。第二期在訊息內帶 epoch 時間並改用 Telegraf json_v2 解析即可根治。
- **傳輸加密**：目前機對機流量全走 Tailscale（WireGuard 加密），故未另配 MQTT TLS 憑證；若未來改走公網 MQTT，須上 8883＋TLS 與每爐獨立憑證。
- **共用橋接帳號**：原型階段所有爐共用一組 burner 帳密；量產應改每爐一組並可個別吊銷。
- **何時才值得換 ThingsBoard／同類平台**：當需求變成「廟方自助新增裝置、客製告警規則、多租戶隔離」時。屆時 Pi 端只要把橋接目標換掉即可，前端投資不浪費。
- **地區地圖**：Grafana Geomap 面板＋各爐經緯度標籤即可做「全台香爐地圖」，屬純加分項，建議放第二期。

## 10. 答詢口袋

「多爐架構三句話：**同一份韌體、身分在設定檔**——新增一台爐只要五分鐘佈建；**斷網不掉資料**——本地佇列＋回線續傳，決策從不依賴雲端；**維運零公網暴露**——工程師經加密私網遠端診斷、更新 Pi 程式、由 Pi 代刷感測韌體，安全層 R4 則刻意設計為幾乎不需更新的底座。」
